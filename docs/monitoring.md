# 新消息快讯监测规则

## 发现与入队

RSS 插件按来源分类轮询 `docs/sources.md` 的 12 个有效订阅（10 个网站），间隔为 5～60 分钟。事件桥按规范化链接去重，移除常见跟踪参数；同一接收会话跨订阅共享去重状态。
首次加入来源时只记录历史基线，已有条目不推送。后续未见链接才检查品种相关性和发布时间。
普通事件要求发布时间有效、不早于发现前 24 小时，且不超过当前时间 5 分钟；不因新闻少或周末而扩大窗口。
入队时的关键词只是候选分类，Agent 读正文后仍可跳过不相关内容。来源失败保留错误，不将失败描述成没有新闻。

暂停来源放在 `docs/sources.md` 的 `paused_feeds`。插件启动时移除本会话对应暂停来源的订阅，保留历史去重状态；恢复时不能清空基线重发旧闻。

## 分档、错峰与 HTTP 冷却

以下是本实例的调度策略，不是来源发布频率或网站允许请求频率的承诺。

| 来源类型 | 订阅 | 名义间隔 |
|---|---|---|
| 快讯 | investingLive News | 5 分钟 |
| 市场报道与技术分析 | investingLive Technical、OilPrice、MarketPulse | 10 分钟 |
| 分析与政策解读 | investingLive Central Banks、FXEmpire Forecasts、ExchangeRates | 15 分钟 |
| 贵金属研究 | GoldSeek、SilverSeek | 30 分钟 |
| 央行原始公告 | Fed、ECB | 30 分钟 |
| 官方能源资料 | EIA | 60 分钟 |

每源的 `poll_minutes`、`poll_offset`、`poll_second` 决定分钟间隔和固定错峰位置；每次调度额外加入 0～30 秒随机抖动。
investingLive 的三个订阅在不同分钟触发。同站 RSS 和文章下载串行执行，两次请求开始时间至少间隔 10 秒，独立网站可以并行。
手动检查只请求到期且未冷却的来源，不能绕过间隔；为容纳两次随机抖动的差异，到期判断允许 30 秒容差。

- HTTP 429：默认从 30 分钟开始指数退避，连续失败依次延长到 60、120、240、360 分钟，默认上限 6 小时；服务端 `Retry-After` 更长时按更长时间等待，支持秒数和 HTTP 日期，并附加少量抖动。
- HTTP 403：同站冷却至少 6 小时，不尝试绕过访问限制。若服务端要求更长等待，同样遵守。
- 超时、网络错误、HTTP 408 或 5xx：从 5 分钟退避，连续失败逐步延长到最多 60 分钟；更长的 `Retry-After` 优先。
- 同站冷却覆盖该网站的其他 RSS 和正文下载。冷却状态保存于 AstrBot 插件数据目录的 `http-state.json`，重启后继续生效。
- 等待冷却不消耗 Agent 处理尝试次数；新闻仍受时效与排队期限约束，过期后跳过。

不计正文请求、异常退避和手动操作时，12 个订阅的理论 RSS 请求量从每小时 360 次降到约 51 次。
降低频率与退避只能减少请求压力，无法保证来源永不返回 429 或封禁。

## Agent 实际执行

1. 插件为新条目建持久任务，下载原文到 `data/raw/YYYY-MM-DD/<job-id>-a<attempt>/`。
2. 插件生成 `runs/YYYY-MM-DD/events/<job-id>.json`，写入原文元数据及三个输出路径。
3. 触发当前 AstrBot 主 Agent，读取 `docs/AGENTS.md`、`docs/event-task.md`、来源范围、整理规则和指定原文。
4. Agent 保存单篇整理稿，按 `docs/news-flash-template.md` 保存“新消息快讯”，并写执行记录。
5. 插件核对整理稿中的原文路径，以及快讯中的必需字段、真实链接、长度和正文范围标记，再读取已保存快讯投递微信。

Agent 不调用子代理、额外模型、联网或消息工具，只读规则与资料、写三个指定输出。
每次只处理一个事件，不创建多品种汇总，不等待每日固定时点。没有新条目时继续轮询，不生成空快讯。
从发现到发送还需要排队、正文下载和 Agent 整理；来源轮询间隔与完整送达耗时分别计算。

## 状态与异常

状态在 `runs/monitor-status.json`，包括 `poll_schedule`、`http_policy` 和来源错误。逐源日志在 `runs/poll-log.jsonl`，记录成功、延期或失败、条目数、HTTP 状态和下次可尝试时间。未到期或冷却中的延期记录不代表已实际发出 HTTP 请求。
微信命令 `/market status` 查看状态；`/market check` 主动检查来源，发现符合条件的新条目仍可入队，但不会重发已处理链接。

- `QUEUED`：待处理。
- `RUNNING`：Agent 正在阅读与整理。
- `RENDERED`：快讯已保存，待投递。
- `BLOCKED_CONTEXT`：微信登录或会话上下文不足，刷新会话后再尝试投递。
- `SENDING`：正在调用平台发送。
- `ADAPTER_ACCEPTED`：适配器接受发送调用，不代表已经送达或已读。
- `UNKNOWN`：发送中断等原因导致结果不确定，不自动重发。
- `FAILED`、`SKIPPED`、`EXPIRED`：失败、不相关或过期，保留原因。

普通排队任务受 `max_queue_age_minutes` 限制，当前配置示例为 120 分钟；处理失败的重试受插件限制。
首次基线、链接去重、任务状态及投递结果由实例收件箱保存，文档更新不清空这些状态。

## 人工端到端验证

验证请求仅由人工明确发起，不等待来源发布新条目。插件数据目录的控制请求使用 `action: test`，可用 `source_id` 指定 `docs/sources.md` 中的有效来源；不接受任意外部地址。
每次请求从该来源的现有 RSS 选择一篇相关候选，以独立验证任务入队，随后复用正文下载、当前 Agent、输出校验和微信投递的实际链路。
事件保留 `test_mode: true`，发送前加上“配置验证｜非新发布新闻”标记，保留原文发布时间；验证不会将旧闻伪装成新发布新闻。
正文不足或不相关时仍可 `SKIPPED`，不会为通过测试放宽内容规则。验证结果结合本次事件、工具轨迹、三个输出文件和收件箱事件记录核对。
`ADAPTER_ACCEPTED` 仍只代表适配器接受发送调用，是否在微信客户端显示须由接收端确认。普通轮询的间隔、HTTP 冷却和投递去重规则继续保留。

## 插件与运行条件

实例使用 `astrbot_plugin_rss` 和 `astrbot_plugin_market_news`。RSS 插件负责调度和解析，事件桥负责收件箱、下载、Agent 调用和统一投递。
RSS 本地补丁将本会话交给事件桥，避免原始标题摘要另行直推，并保留 TLS 校验和日期解析处理。
安装与版本见 `plugins/README.md`，来源验证见 `docs/source-validation.md`。升级插件前检查本地补丁与集成兼容性。
电脑、Docker、AstrBot 和网络需保持运行；轮询与投递由现有插件持续执行。
